# 麦门省钱与性价比推荐助手

## 技能目的

帮用户在海量麦当劳餐品与当日优惠中，快速找到**"今天最值的那个方案"**，而不只是列菜单。
核心产出是一份**当日性价比榜单**：每个推荐方案都要给出性价比分、适合人群、推荐星级，让用户"看得懂为什么值"。

## 查询模式：实时为主，定时为辅

本技能有且仅有一种数据获取方式 —— **实时调用麦当劳接口**。任何时刻被触发，都要当次重新拉取数据，不使用缓存、不沿用上次结果。

| 模式 | 触发 | 行为 |
|------|------|------|
| **实时查询（主要）** | 用户随时提问（"今天吃啥""帮我看看现在有啥券"） | 立即调用接口，拉当前时刻的菜单+券+价格，现场算分出榜单 |
| **定时推送（辅助）** | 每天 12:00 由定时任务触发 | 同一套实时逻辑跑一遍，把榜单主动推给用户 |

**关键**：
- 12:00 的定时推送**不是**数据来源，只是"到点自动帮你问一次"
- 用户在任何其他时间提问，都要**实时重新查询**，结果可能与 12:00 那份不同（券会变、餐品会下架、价格会变）
- 不在非 12:00 的时刻说"请等今天 12 点的榜单" —— 直接现在就算
- 每次输出都标注查询时间（如"数据时间：今天 15:32"），让用户知道是实时的

## 何时使用

- 用户想吃麦当劳，但不知道点啥 / 问"今天有什么划算的"
- 用户问"哪个套餐最值""性价比最高的组合""帮我搭配一个套餐"
- 用户有预算约束："30块怎么吃好""20元以内推荐"
- 用户有场景约束："一个人吃""两个人""减脂""管饱""下午茶"
- 用户问"麦门有什么券""怎么点最省钱"
- 用户确认推荐后想直接下单

## 核心工作流

### 第 0 步：确认场景参数（能推断就推断，不要连环追问）

推荐前需要确定 4 个参数，缺失时按下面规则处理：

| 参数 | 取值 | 缺失时处理 |
|------|------|-----------|
| 门店 | storeCode | 用 `mcp__mcd-mcp__query-nearby-stores`（searchType=1 收藏店优先，无收藏则 searchType=2 按城市+关键词搜） |
| 取餐方式 | beType | 默认 **1-到店自取**（性价比最高）。用户提到"送家里/公司"→ 2-麦乐送 |
| 预算 | 元 | 未提及则不设硬上限，按性价比排序自然覆盖各价位 |
| 场景/人数 | 单人/双人/减脂/管饱等 | 未提及则按**单人常规正餐**处理 |

**追问原则**：只有当"门店"和"取餐方式"都完全无法确定时才问一次，且合并成一句话问。其余参数一律用合理默认值先跑，跑完在结果里说明"如需按送餐/减脂调整可告诉我"。

### 第 1 步：拉取当日菜单与优惠

按当前时间与取餐方式调用：

1. `mcp__mcd-mcp__query-meals` — 拉取门店在售餐品（含套餐、单品、随单购），拿到 `productCode` 与基础价
2. `mcp__mcd-mcp__query-store-coupons` — 拉取**该门店+该取餐方式**下可用的优惠券
3. `mcp__mcd-mcp__available-coupons` — 查看用户当前**可领取**的优惠券（若有可领的券能显著提升性价比，提示用户"先领券再下单"）
4. `mcp__mcd-mcp__query-my-coupons` — 查看用户卡包已有券（与上一步合并去重使用）

> 参考 `references/api-reference.md` 了解各接口的参数传递规则与返回结构。

### 第 2 步：计算性价比评分

对候选方案（套餐 + 可能的单品组合）逐个计算。**评分口径见 `references/scoring-model.md`**，核心公式：

```
性价比分 = 饱腹价值 × 0.4 + 优惠力度 × 0.3 + 营养均衡 × 0.2 + 场景契合 × 0.1
```

- 用 `mcp__mcd-mcp__calculate-price` 拿到**含券实付价**（返回单位为**分**，展示时 ÷100 转元）
- 用 `mcp__mcd-mcp__list-nutrition-foods` 拿到热量/蛋白质等营养数据，用于"减脂/管饱"维度的判断
- 可用 `scripts/value_score.py` 做批量评分与排序（传入候选 JSON，输出排序后的榜单）

**关键：必须用真实价格计算，不要凭记忆估价格。**

### 第 3 步：输出结果（默认：交互式查询网页）

**默认产出交互式 HTML 查询页**（用户要求"可以输出一个网站查询"）。流程：

1. 把候选方案整理成 JSON（字段见 `scripts/render_board.py` 头部注释）
2. 运行渲染脚本生成交互页：
   ```bash
   python scripts/render_board.py candidates.json -o mcd_query_$(date +%Y%m%d_%H%M).html \
       --store "门店名（到店自取）" --when "$(date '+%Y-%m-%d %H:%M')"
   ```
3. **用 present_files 打开这张 HTML**，用户在预览面板里即可交互查询
4. 同时在对话里附前 3 名的精简文字摘要

查询页提供的交互能力：
- **预算滑块**：拖动即可实时过滤该预算内最值的方案
- **场景标签**：点选 学生党/上班族/减脂/双人/下午茶 等，榜单实时重排
- **排序切换**：性价比↓ / 价格↑ / 省最多 / 热量↓ 四种排序
- **详情展开**：点"详情"展开完整组成、营养数据、用券明细、适合人群标签

**仅在用户表示"文字就行"时，才只输出纯文字榜单。**

纯文字版（备用）格式：

```
🏆 今日最值 · 方案名
├ 套餐包含：
│   ├ 主食：双层吉士堡 ×1
│   ├ 小食：中薯条 ×1
│   └ 饮料：中可乐 ×1
├ 原价 ¥xx → 实付 ¥xx（省 ¥xx，用券：xxx）
├ 性价比分：8.7/10
├ 适合人群：xxx
└ 推荐程度：★★★★★ 闭眼冲
```

- **套餐包含**必须逐项列出，标注**品类（主食/小食/饮料/甜品）+ 名称 + 数量**，不能只写"含汉堡薯条饮料"
- 组成信息来自 `mcp__mcd-mcp__query-meal-detail`；套餐内可换的选项用"（可选：xxx / xxx）"标出
- **推荐程度用 5 星制**，与性价比分对应（换算与话术见 `references/scoring-model.md`）
- **适合人群**必写，且要具体（如"赶时间的上班族""两人分享""健身增肌"），不要写空话
- 榜单建议给 **3–5 个方案**：头名 + 不同预算档/不同场景各一个，覆盖用户可能的需求
- 明确标注**"今日限定"**信息（如当日券、限时促销的起止时间）

### 第 4 步：给出省钱建议（可选增强）

- 若用户有可领券：提示"先领这张券，能再省 X 元"
- 若组合比套餐更划算（如单品+随单购）：说明"拆开点比套餐便宜 X 元"
- 若量大更划算：给出"多买一份的人均成本"对比
- 提醒优惠券的**有效期**和**使用门槛**

### 第 5 步：下单（仅用户确认后）

用户说"就要这个""帮我下单"后：
1. 复述最终方案与实付价，确认无误
2. 调用 `mcp__mcd-mcp__calculate-price` 复核价格
3. 调用 `mcp__mcd-mcp__create-order` 创建订单（到店场景需传 `takeWayCode`，来自 calculate-price 返回的 `takeWayList`）
4. 引导用户完成支付，并告知可回复"支付完成"查询订单

## 图形化 / 交互式展示（默认输出形式）

用户要求"更直观""可以输出网站查询"，因此**默认产出交互式 HTML 查询页**，而不是纯文字。要点：

- 用 `scripts/render_board.py` 渲染成一张自包含 HTML（内联 CSS/JS，无外部依赖，双击即可打开）
- 渲染后用 `present_files` 打开，用户在预览面板直接交互
- **交互能力**：预算滑块筛选、场景标签筛选、四种排序切换、套餐详情展开
- **视觉元素**：排名奖牌（🥇🥈🥉）、左侧推荐等级色条、性价比分进度条、四维子分标签、品类图标（🍔主食 / 🍟小食 / 🥤饮料 / 🍦甜品）
- 视觉逻辑（**遵循中国用户习惯**）：
  - **红色 = 最值得/最优**（推荐度最高），醒目突出
  - 橙色 = 强推，黄色 = 推荐，灰色 = 一般/不推荐
  - 实付价用红色大号字体强调，省钱用红色徽章
- 顶部"实时数据 · 查询于 …"绿色脉冲标识，标明数据新鲜度
- 一次推荐多个方案，全部渲染进**同一张** HTML（查询页形态），不要一个方案一张图

> **重要**：查询页是静态产物，数据由 AI 在生成时从麦当劳接口实时取得。页面本身不直接调接口（麦当劳官方 MCP 不支持前端直连）。用户想刷新数据，重新让技能跑一次即可。

## 套餐内容展示规则（用户重点关注）

用户非常在意"这个套餐里到底有啥"，展示时必须做到：

1. **逐项列出**：主食、小食、饮料、甜品分开写，标名称和数量，例如
   - 主食：板烧鸡腿堡 ×1
   - 小食：中薯条 ×1
   - 饮料：中杯可口可乐 ×1
2. **不要概括**：禁止用"含汉堡+薯条+饮料"这种笼统写法代替具体品名
3. **可选项要标注**：套餐内可替换的（如饮料可选可乐/雪碧/零度）用"（可选：…）"列出
4. **数据来源**：套餐组成取自 `query-meal-detail` 返回的 choices/roundList；单品信息取自 `query-meals`
5. **规格说明**：尽量标明规格（中杯/大杯、中薯/大薯），帮助用户判断实付价是否划算

若某套餐无法取到组成明细，明确写"组成明细暂缺"，不要编造。

## 定时推送（每天 12:00，仅辅助）

技能支持被定时任务调用，在**每天中午 12:00 自动**生成并推送一份当日榜单，省得用户自己开口。

- 定时任务走的是与实时查询**完全相同**的实时流程（当次拉接口），不是读缓存
- 默认参数：到店自取 + 单人常规正餐
- 用户如在推送后回复调整（如"改成麦乐送""帮我下单"），继续按正常流程**重新实时查询**后处理
- **再次强调**：定时推送只是"到点自动问一次"。用户在任意时间主动提问，都必须实时查询，不要引导用户"等 12 点的推送"

## 重要规则

- **实时优先**：每次触发都当次重新查接口，绝不使用缓存或复述历史结果；输出须标注"数据时间"
- **价格一律以接口返回为准**，不猜测、不沿用历史价；单位为分时务必 ÷100
- **券优先**：同时考虑"已持有券"和"可领取券"，可领券要在推荐中体现
- **不虚构餐品**：只推荐 query-meals 返回的在售商品
- **显示优惠来源**：每个省下的钱都要说明来自哪张券/哪个活动
- **推荐程度要有区分度**：不要所有方案都五星，需拉开梯度
- **减脂场景**：热量数据必须来自 list-nutrition-foods，不要编造
